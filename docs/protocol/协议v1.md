# Secure Communication 协议 v1

状态：1.0 基线  
外层媒体类型：`application/sc-envelope+json`  
固定入口：`/sc/v1/handshake`、`/sc/v1/handshake/finish`、`/sc/v1/message`

协议 v1 运行在经过认证的 TLS 1.2 或更高版本之上，提供服务端身份固定、安装身份
持有证明、业务载荷机密性与完整性以及重放保护。协议不提供旧传输兼容、明文回退或
算法降级。Spring Boot、Go 和 Python 服务端以及全部客户端 SDK 共享本规范。

## 1. 密码套件与握手

1.0 必选套件为 `P256_HKDF_SHA256_AES256_GCM`。预留的
`SM2_SM3_SM4_GCM` 标识只有接入经过审计的 Provider 后才能启用，当前版本不交付
该实现。

握手开始请求包含：协议版本、套件、app/device 标识、设备类型、P-256 临时 SPKI、
安装签名 SPKI、可选的一次性注册令牌和毫秒时间戳。服务端返回固定身份 SPKI、临时
SPKI、key/session ID、创建与过期时间，以及 64 字节 P1363 ECDSA transcript 签名。

客户端必须先核对 `kid` 与固定信任锚、验证 transcript 签名，再派生会话材料，并在
`/sc/v1/handshake/finish` 使用安装私钥证明持有身份。非 H5 新安装还必须在握手开始
阶段消费短时、单次注册令牌；H5 通过受信 Origin 准入。

国际套件使用 P-256 ECDH 共享秘密和 HKDF-SHA-256：

- salt：握手 transcript 的 SHA-256；
- info：`SC1/session/<suite>/<sid>`；
- 输出：72 字节，依次拆分为 32 字节请求密钥、32 字节响应密钥、4 字节请求 nonce
  前缀和 4 字节响应 nonce 前缀。

## 2. 加密信封

严格 JSON 信封必须且只能包含以下字段：

```json
{
  "v": 1,
  "suite": "P256_HKDF_SHA256_AES256_GCM",
  "kid": "server-key-2026",
  "sid": "opaque-session-id",
  "ts": 1785283200000,
  "seq": 1,
  "rid": "transport-request-id",
  "m": "POST",
  "p": "/sc/v1/message",
  "cty": "application/sc-protected+json",
  "st": 0,
  "nonce": "base64url-12-bytes",
  "ct": "base64url-ciphertext-and-tag"
}
```

`m`、`p`、`cty` 是固定传输绑定，外层不会泄露业务路由。`rid` 是可见但经过 AAD
认证的传输请求 ID。请求的加密明文为：

```json
{
  "method": "POST",
  "path": "/attach/upload",
  "contentType": "application/json",
  "headers": {"code": "protected-value"},
  "body": "base64url-business-body"
}
```

服务端把认证后的 `rid` 作为 `x-sc-request-id` 交给业务处理器。响应加密明文只包含
规范化后的 `contentType` 和 Base64URL body。浏览器控制的 `Origin`、`Referer`、
`Sec-Fetch-*` 保持在外层，只用于浏览器准入，不能作为密码学身份凭据。

## 3. Nonce 与 AAD

Nonce 固定为 `4-byte direction prefix || uint64_be(seq)`。同一会话中请求和响应使用
不同密钥与不同前缀；序号从 1 开始，不能复用。

请求 AAD 使用换行连接以下字段：`SC1`、`request`、suite、kid、sid、timestamp、
sequence、request ID、固定外层 method、固定消息 path、受保护媒体类型。响应 AAD
把方向改为 `response`，并在末尾追加逻辑 HTTP status。

服务端必须先完成信封、nonce 和 AEAD 认证，再原子认领 `session + direction + seq`。
认证失败的密文不能占用重放序号。

## 4. 路由、重试与错误

全部逻辑请求都通过 `POST /sc/v1/message`。只有解密并认证后的 method 和规范化 path
通过宿主白名单后，才能转发给业务 Handler、Controller 或 ASGI 应用。宿主仍必须在
网关或应用边界阻断外部直接访问原明文业务入口。

SDK 不自动重试业务 POST。业务队列重试时必须使用新的传输序号和 `rid` 重新加密，
同时保留原业务 message、batch 或幂等 ID。会话过期、撤销或未知时必须重新握手。

任何认证、路由或套件失败都不能触发协议降级。错误响应只暴露稳定安全错误码和可选
trace ID，不返回或记录明文、密钥、注册令牌、Redis key 与 Provider 异常详情。完整
错误表见[协议错误码](协议错误码.md)。
